# Contributing

Thanks for helping! This is a **matching** decompilation: every C file must compile, with the
original compiler, into exactly the bytes of the retail executable. The build checks it for you.

## What you need

- Your own copy of **Kingdom Hearts Final Mix** (Japan), and its `SLPS_251.98` extracted from the disc.
  Never share or commit it, or any other game file.
- Podman or Docker (or the tools from `docker/Containerfile` installed locally).

Setup is in the [README](README.md). From then on, everything runs inside the container:

```sh
podman run --rm -it -v "$PWD":/work:Z kh1fm bash
./configure.py      # once, and after editing config/
ninja               # must end with "build/SLPS_251.98.rom: OK"
```

## Picking something to work on

1. Look at the open issues labelled **claim**: each one is a file or module. Comment to take it,
   so nobody works on the same functions twice. If what you want is not listed, open an issue.
2. Good first targets are files that already exist in `src/` with `INCLUDE_ASM` lines left:
   `python3 tools/funcs.py game/area` lists which functions of a file are done.
3. Carving a new file out of the asm blocks needs its boundaries (see below): ask first if unsure.

## Decompiling a function

```sh
python3 tools/m2c.py game/area func_00112820   # first draft from m2c
# replace the INCLUDE_ASM line in src/game/area.c with your C
ninja build/src/game/area.o
python3 tools/diff.py game/area func_00112820   # expected vs built, differing lines only (-a: all)
```

- `tools/try.py <unit> <function> <file>` compiles several alternative bodies (separated by `----`
  lines) and prints how many lines differ for each; handy for ordering and register-allocation fights.
- The objdiff GUI works too: open the repository folder; `objdiff.json` is generated by `configure.py`.
  Its "decomp.me" button creates a scratch with the right compiler and context.
- `ninja report && python3 tools/progress.py` shows overall progress.

When `tools/diff.py` reports `0 differing lines` (a line differing only in a relocation name such as
`<.text>` vs `<func_...>` is fine) and the full `ninja` ends with `OK`, the function matches.

## Things that matter with ee-gcc 2.96

- Float constants are converted by **truncation**: write the plain value (`0.05f`), not a corrected one.
- Struct field accesses and plain pointer/scalar accesses are aliased differently, which changes how
  loads and stores are ordered. Flags that are read back after a write are usually bitfields.
- Copy small structs field by field: a struct assignment becomes unaligned 64-bit loads.
- `array[index].field` and a local pointer to the element compile with operands in a different order.
- If only a construct no programmer would write matches (`do { } while (0)`, a pointless temporary),
  keep it and mark the line with `// TODO fake match`.

## Style

- Names: `Module_Action` for functions (`Area_Setup`), `g_Name` for globals, `unk_XX` for unknown
  struct fields at offset `XX`, and keep `func_XXXXXXXX` / `D_XXXXXXXX` until the purpose is clear.
- Every struct field gets its offset in a comment, and every struct its size.
- Add each name you give to `config/symbol_addrs.txt`.
- A short comment at the top of each file saying what the module does.
- This project is written from the executable: do not copy code, headers or structure definitions
  from other decompilations unless their license allows it, and say where it comes from.

## Finding file boundaries

The game code is still one large asm block. ee-gcc aligns every function to 8 bytes, so padding does
not reveal where one object file ends. What does: functions sharing the same block of `.data` /
`.rodata` / `.bss` variables, string literals stored in order, and static helpers used by a single
group. `tools/strrefs.py` lists which function uses which string.

## Pull requests

- Before opening one: `./configure.py && ninja` must end with `OK` on your machine.
- CI does **not** run on pull requests (the runner holds the retail executable); a maintainer
  re-checks after merging.
- One file or module per pull request when possible. By contributing you agree to release your
  work under [CC0](LICENSE).
